# Vespera V2 Money — план версии «на $100k»

Ветка: `V2money` (от `main` 0.26.0 + #28). Дата плана: 2026-11-03.
Статусы как в [ROADMAP](../ROADMAP.md): «код готов» ≠ «проверено на реальных
данных» ≠ «доказан перевес».

## 0. Суть

Покупатель платит $100k не за интерфейс, а за **доказанный перевес**. V2 переводит
Vespera с «угадывания направления по SMA» на три источника денег, которые дают
сами правила рынка:

1. **Справедливая цена** рынка Up/Down по источнику расчёта (Chainlink TWAP).
2. **Маркет-мейкинг**: мейкеры не платят комиссию и получают ребейты и награды.
3. **Арбитраж** внутри рынков и между логически связанными рынками.

Всё это проверяется **честным бэктестом на реальных стаканах Polymarket**.
Реальные деньги включаются только после статистического «сертификата перевеса».

## 1. Почему меняем ядро

Наши замеры (данные в `/data/audit/bt`, 2026-11):

- SMA 20/200 за год: 5m — 48,8% побед (n=4537), 15m — 46,5% (n=1554),
  1h — 46,4% (n=730). Безубыточность при цене 0,50 и комиссии — **51,75%**.
- Walk-forward: в выборке 57–67%, вне выборки 45–56%, значимых нет.
- Исход по Binance не совпал с расчётом Polymarket в 8 из 181 рынков: Polymarket
  считает по Chainlink TWAP, а не по свече Binance.
- Мартингейл ×2 за год: −$657 (19 обнулений серии) против −$162 у фиксированной
  ставки.

Внешние данные:

- OpenMarket: модель на 43 признаках потока Binance не обыграла цену самого
  Polymarket вне выборки, симуляция торговли в минус; котировки Polymarket
  догоняют резкие движения Binance в среднем за 347 мс.
- Комиссия тейкера в крипторынках: `C × 0,07 × p × (1 − p)` (до 1,75¢ за акцию
  при p = 0,50). Мейкеры комиссию не платят и делят 20% комиссий тейкеров.
- Арбитраж на Polymarket: реализовано около $40 млн прибыли; в идеальной модели
  комбинаторного арбитража — 3,5% в неделю после спредов и комиссий; реальный
  объём ограничен глубиной стакана.
- Покупки дешевле 10¢ теряют 19,3¢ на доллар, от 90¢ — дают +0,83¢
  (588 млн сделок; эффект устойчив в крипторынках).

## 2. Критерии «стоит $100k»

Целевые значения, уточняются после M1:

| # | Критерий | Цель |
|---|---|---|
| 1 | Перевес вне выборки после комиссий и проскальзывания | > 0, значим после поправки на множественные проверки (p < 0,01, Deflated Sharpe > 0,95) |
| 2 | Объём проверки | ≥ 2000 сделок (тейкер) или ≥ 30 дней котирования (мейкер) |
| 3 | Трек-рекорд в работе | ≥ 60 дней пилота на реальных деньгах в пределах 95% интервала симуляции |
| 4 | Риск | просадка ≤ 15% выделенного капитала при ¼ Келли; риск разорения < 1% (Монте-Карло) |
| 5 | Прозрачность P&L | разбивка: спред, ребейты, награды, направление, комиссии; сверка с исполнениями в блокчейне до цента |
| 6 | Надёжность | доступность сервера ≥ 99,5%; ноль неразобранных «неизвестных» ордеров |

## 3. Принципы V2

Инварианты из [ROADMAP §0](../ROADMAP.md) сохраняются полностью (один
исполнитель, без автоперехвата, без слепого повтора POST, неизвестное исполнение
не снимается ИИ/Telegram). Дополнительно:

- **Paper и real — один код.** Paper исполняет по реальному стакану, а не по 0,50.
- **Реальный Start — только с действующим сертификатом** для конкретной версии
  настройки (fingerprint из `setupStore`).
- **Каждое денежное решение объяснимо в журнале:** справедливая цена, перевес,
  комиссия, размер, причина.
- **Без мартингейла по умолчанию.** ×2/Recover остаются только как legacy с
  предупреждением.
- **Не обещаем прибыль:** показываем доверительные интервалы, а не одну цифру.
- **Параметры рынка — из API** (комиссия, ребейты, настройки наград), не константы.

## 4. Этапы

### M0. Данные — фундамент

Что делаем:
- Сборщик 24/7 на сервере: стаканы и сделки Polymarket CLOB (WebSocket) по
  рынкам Up/Down BTC/ETH/SOL/XRP × 5m/15m/1h/4h/день.
- Chainlink: цена и TWAP через PolyBolt (`price.crypto`, `price.crypto.twap`).
- Binance: сделки и лучшая цена (ведущий индикатор).
- Метаданные рынка: цена старта, время, комиссия, настройки наград.
- Исполнения из блокчейна (`OrderFilled`): направление сделки по публичному
  потоку верно лишь в ~59% случаев.
- Хранилище по дням (Parquet/SQLite), контроль пропусков, контрольные суммы.
- Импорт открытых данных: OpenMarket (BTC 15m, 727 млн строк) и Polymarket-v1
  (1,2 млрд сделок).

Где в коде: новый `src/data/` (сборщики, хранилище), `markets.js`,
`marketData.js`, `brokers/clobClient.js`.

Готово когда: 14 дней сбора без пропусков > 5 с; исходы, восстановленные по
Chainlink, совпадают с официальными в 100% рынков; нагрузка сервера в норме.

### M1. Честный бэктестер

Что делаем:
- Пошаговый повтор событий по реальному стакану: тейкер исполняется по глубине,
  мейкер — по позиции в очереди с учётом отмен.
- Комиссия по формуле рынка, настраиваемая задержка (100–500 мс), расчёт по
  правилу Chainlink (итог ≥ цены старта → Up).
- Статистика: walk-forward, purged/embargo CV, бутстрэп-интервалы,
  Deflated Sharpe, PBO (CSCV), поправка Holm/BH на множественные проверки.
- Лаборатория (`researchRunner.js`, `researchStore.js`) переходит на новый движок;
  модель Binance/0,50 остаётся быстрым режимом с пометкой «приблизительно».

Готово когда: повтор текущей SMA-стратегии совпадает с журналом Paper в пределах
допуска; отчёт показывает интервалы и p-value; месяц данных одного рынка
считается быстрее минуты.

### M2. Справедливая цена

Что делаем:
- Модель P(Up) как цифрового опциона на Chainlink TWAP: текущая цена, цена
  старта, остаток времени, волатильность (EWMA, HAR-RV, режимы), толстые хвосты
  (Student-t/скачки), поправка на усреднение TWAP в конце окна.
- Калибровка: кривая надёжности, Brier и log-loss. Эталон — середина стакана
  Polymarket (её трудно обыграть, это и есть планка).
- Применение: фильтр входа (перевес > комиссия + проскальзывание + запас), центр
  котировок для M3, показ в UI и журнале.

Где в коде: `src/main/models/fairValue.js`, подключение через `strategy.js` и
`strategies/`.

Готово когда: на отложенной выборке ошибка калибровки (ECE) ≤ 2%, log-loss не
хуже середины стакана; фильтр улучшает результат вне выборки.

Замеры (3 ноября, живые данные Polymarket):
- Цена старта K — значение потока Chainlink TWAP-60 (RTDS
  `crypto_prices_twap_sixty`) ровно в секунду старта окна. Совпало с Gamma
  `priceToBeat` точно в 30 окнах из 30 (7 активов, 5m и 15m). Gamma заполняет
  `priceToBeat` только к концу окна, `finalPrice` ещё позже. Поэтому K живого
  окна берём из потока в секунду старта. Binance и базис для K не нужны.
- Итог: TWAP-60 в секунду конца ≥ K → Up. Совпал с официальным исходом в 34
  окнах из 34.
- Комиссия тейкера: `shares × 0.07 × p × (1 − p)` USDC. На реальных сделках
  RTDS медиана отношения к формуле ровно 1.000. В Gamma у всех 5m/15m рынков
  `feeSchedule {rate 0.07, exponent 1}`, минимум 5 шт.
- Стакан: биды UP = 1 − аски DOWN с теми же объёмами. Часть изменений приходит
  только по токену DOWN, поэтому книгу UP собираем из обоих токенов. В 18
  проверках из 18 книга совпала с REST `/book` уровень в уровень; поток WS
  отстаёт от метки REST примерно на 0,1 с.
- Волатильность: секундные приращения Chainlink автокоррелированы. Отношение
  дисперсий 60 с / 1 с — от 1,5 до 3,4, то есть σ по 1-с шагам занижает риск
  на 60 с в 1,2–1,8 раза. Модель берёт σ по перекрывающимся 60-с приращениям
  за час (нужно ≥ 5 мин данных).
- Paper-проверка на 14-минутной записи (22:20–22:35 UTC): 14 входов с перевесом
  ≥ 3% после комиссии по реальному стакану. По официальным итогам 5 в плюс,
  −$13,50 на $38,50; средний markout за 30 с −6,5%. Модель только на Chainlink
  здесь проиграла стакану: рынок учитывает данные, которые опережают Chainlink.
  Выборка короткая и связанная, но перевеса не видно. Значит, M2 нужны
  опережающие источники и честная калибровка, а не только TWAP-модель.
- У открытых рынков Gamma `outcomePrices` и `bestBid`/`bestAsk` отстают, и
  `prices-history` тоже. Живую цену берём из CLOB (WS `book`/`price_change`).
- Темы цен RTDS переезжают в PolyBolt (нужны ключи). Серверной версии нужен
  PolyBolt.

### M3. Маркет-мейкер

Что делаем:
- Котировки вокруг справедливой цены: оптимальный маркет-мейкинг для бинарных
  рынков (logit-пространство, запас позиции, время до расчёта), сдвиг котировок от
  запаса (Avellaneda–Stoikov), ширина от волатильности и «токсичности» потока.
- Управление заявками: post-only, отмена/замена, лимиты API, аварийная отмена
  всех заявок при скачке Binance/Chainlink, прекращение котирования за N секунд
  до конца окна.
- Учёт доходов: спред, maker rebates, liquidity rewards — со сверкой выплат.
- Метрики: markout через 1/10/60 с, доля исполнений, захваченный спред.
- Запуск по ступеням: симуляция → «тень» (котировки считаются, но не ставятся) →
  пилот малыми суммами с жёсткими лимитами.

Где в коде: `strategies/maker.js`, менеджер заявок в `brokers/`, `fees.js`.

Готово когда: в симуляции и «тени» чистый результат > 0 после неблагоприятного
отбора вне выборки; 14 дней пилота в пределах 95% интервала симуляции.

### M4. Сканер арбитража

Что делаем:
- Тип A: в одном рынке YES + NO дешевле $1 (или дороже — разделение и продажа).
- Тип B: рынки с несколькими исходами (negRisk): сумма вероятностей ≠ 100%,
  конвертация NO → YES.
- Тип C: связанные рынки — лестницы «выше X», диапазоны, «к дате». ИИ извлекает
  связи из правил рынков → проверка правилами и человеком → решатель
  (целочисленное программирование, HiGHS/OR-Tools) собирает портфель с учётом
  глубины и комиссий.
- Исполнение по ногам с лимитом риска незакрытой ноги и планом отката; учёт
  заморозки капитала до расчёта (доходность в годовых).

Где в коде: новый `src/main/arb/` (граф связей, решатель, исполнитель).

Готово когда: повтор по истории находит возможности, сопоставимые с
исследованиями; 14 дней в режиме «только сигналы» с оценкой реально исполнимого
объёма; затем исполнение малыми суммами.

### M5. Риск и капитал

Что делаем:
- Ставка по Келли для покупки по цене p при оценке вероятности q:
  `f* = (q − p′) / (1 − p′)`, где p′ — цена с комиссией. По умолчанию ¼ Келли,
  сжатие оценки перевеса при неопределённости.
- Лимиты: на сделку, рынок, кластер связанных активов (BTC/ETH/SOL/XRP), дневной
  лимит убытка, предохранитель по просадке.
- Распределение капитала между стратегиями (тейкер, мейкер, арбитраж) и рынками.

Где в коде: `risk.js`, `money.js`, `stats.js`.

Готово когда: Монте-Карло показывает риск разорения < 1% при заданных лимитах;
каждый размер объяснён в журнале.

### M6. Допуск к деньгам и контроль

Что делаем:
- «Сертификат перевеса» для версии настройки: минимальный объём, значимость после
  поправок, совпадение Paper ↔ симуляция. Без сертификата реальный Start
  недоступен — на сервере и в приложении.
- Контроль в работе: SPRT/CUSUM по реализованному перевесу, дрейф калибровки и
  признаков, автопауза и сообщение в Telegram, ежедневный отчёт.

Готово когда: искусственное «затухание» перевеса в тесте вызывает автопаузу;
сертификат проверяется в обоих исполнителях.

### M7. Интерфейс профи

- Панель: справедливая цена против рынка, перевес, позиции и запас, свои заявки в
  стакане, P&L по источникам, markout.
- Лаборатория: выбор данных, walk-forward, статус сертификата.
- Портфель: все рынки и стратегии на одном экране.
- Telegram: отчёты по источникам P&L, сертификату и автопаузам.
- Экран «Движок» (`tools/engine-viz/`, работает на живых данных Polymarket без
  ключей):
  1. нити — каждая реальная сделка любого рынка: кошелёк → (время до итога,
     цена YES/UP) → её событие на кольце;
  2. кольцо — все открытые события Polymarket (около 17 тыс.) по разделам;
     крутится мышью (ЛКМ с инерцией, колесо, Ctrl+колесо — масштаб,
     мини-карта); у крипто-окон 7 активов × 5m и 15m: K, модель, перевес,
     позиция paper и причина, если входа нет;
  3. лучи — стакан рынка в фокусе по уровням (BTC — всегда), у остальных
     последние сделки;
  4. панели — потоки и задержки, Chainlink и TWAP с K, граф модели, стакан,
     кошельки, paper.

  Запись и повтор (`record.mjs`, `?replay=`) идут через тот же движок, кадр в
  кадр. Для боевой версии нужен поток событий движка с сервера: свои заявки,
  исполнения, P&L, статус сертификата.

### M8. Расширение (после ядра)

- Справедливая цена для рынков «BTC выше X к дате» из опционов Deribit.
- ИИ-прогнозы событийных рынков: ансамбль агентов + цена рынка + учёт Brier —
  только через сертификат.
- Радар «умных денег» по данным блокчейна.
- Пульт оператора для нескольких клиентов.

## 5. Порядок и сроки (оценка)

| Недели | Этап |
|---|---|
| 1–2 | M0: сборщик запущен и дальше работает постоянно |
| 2–5 | M1 бэктестер; M5 Келли и лимиты |
| 4–7 | M2 справедливая цена |
| 6–9 | M6 сертификат и контроль |
| 7–12 | M3 маркет-мейкер: симуляция → тень → пилот |
| 8–12 | M4 арбитраж: сигналы → малые суммы |

| 13–22 | Трек-рекорд 60 дней; M8 по готовности |

Сбор данных стартует первым: без недель реальных стаканов M1–M4 проверять не на чем.

## 6. Риски

| Риск | Что делаем |
|---|---|
| Быстрые боты (реакция рынка ~350 мс) | замер задержки до CLOB, сервер ближе к Polymarket при необходимости, аварийная отмена заявок |
| Мало ликвидности | считаем исполнимый объём, а не теоретический |
| Polymarket меняет комиссии/ребейты, «fee holiday» без ребейтов | параметры из API рынка, пересчёт перевеса на лету |
| Переобучение | отложенные выборки, поправки на множественные проверки, сертификат |
| Ресурсы сервера (2 vCPU / 1,9 ГБ) | отдельный диск или апгрейд под сбор данных |
| Гео-ограничения площадок | существующий preflight и регулярная проверка доступа |

## 7. Вне рамок этого плана

Подписки, лицензирование и усиление безопасности — отдельным планом. Действующие
правила безопасности исполнения при этом не ослабляются.

## 8. Работа с веткой

- `V2money` — интеграционная ветка. Этапы идут отдельными ветками
  (`v2/m0-data`, `v2/m1-sim`, …) через PR в `V2money` с CI на трёх ОС.
- `main` остаётся рабочей версией для клиентов. `V2money` → `main` только после
  сертификата и пилота.
- Для разработки нужен push-доступ по ключу развёртывания: крупные файлы
  (`engine.js`, `renderer/app.js`, `i18n.js`) через текущий инструмент GitHub не
  отправить.
